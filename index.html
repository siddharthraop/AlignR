Abstract

Each new Cloud TPU generation gets a set of topics with the same structure as the last one and new values. The v5p, v6e and TPU7x pages share one skeleton: an introduction, a system architecture table, configurations and a VM section234. Writers build each new set by copying the last one and editing it by hand. Labels drift and values get typed twice.

AlignR is an agent that drafts the new set from the existing DITA topics. It finds sibling topics of the same type, reads the new values, and asks Gemini to fill a JSON Schema that mirrors the DITA content model. Gemini never writes XML. A plain Python serialiser writes it, with a key reference for every value that has a key. The topic then passes the DITA RELAX NG grammar, house rules in Schematron, a grounding check and Vale before a writer sees it as a pull request.

The original AlignR design aligned a model by fine-tuning on 12,000 to 20,000 preference pairs5. This version keeps its preference pair format and drops the training. Every writer edit to a draft is logged as a pair. A fixed rule (§5.9) decides when the log is large enough, and good enough, to pay for tuning.

§1 Client Brief

The client is Google's data center products and services documentation. The sample content is the Cloud TPU documentation for three hardware generations: TPU v5p, TPU v6e (Trillium) and TPU7x (Ironwood)234. The MANIFEST project converted this content to DITA, with generation values stored once as keys6.

It is a good test for two reasons. First, the generations repeat a structure, so there are real siblings to learn from. Second, the answer exists. AlignR holds out TPU7x, drafts its topics from the v5p and v6e topics and the TPU7x values, and compares the draft with the page Google published. That page was last updated on 13 October 20262.

§2 Problem Statement

A new hardware generation is the most predictable writing job in data center documentation. The topic set is known in advance. The structure is the same as last time. Only the values and a few new concepts change. Today that predictability is used by hand: a writer copies the previous set and edits it.

2.1 Same skeleton, new values

Figure 2 lines up the three TPU generation pages as Google publishes them. Every page has the same four slots. The labels in those slots have drifted, because each page was written separately.

Headings and first sentences as published on 13 October 2026234. Four slots repeat on every page. The purple sections are where a writer's knowledge is needed most, and where no sibling exists to learn from.
A real example
The TPU7x page states its memory values twice. The specification table gives HBM capacity as 192 GiB and bandwidth as 7380 GBps. The memory hierarchy section below it says each chip has 192 GB of HBM, with bandwidth of approximately 7.37 TB/s2. GiB and GB are different units. When a value is typed into prose, it can drift from the table. When it is a key, it can't.

The skeleton stays. The values move a lot from one generation to the next (Figure 3). In a DITA set every one of these numbers is a key, so a new generation adds a column of values, not a new structure.

Figure 3

Problem statement
Each new TPU generation needs a topic set with the same structure as the last and new values. Writers build it by copying and editing by hand, so labels drift and values get typed twice. A general model drafts faster, but its output is not valid DITA and its values have no source. Fine-tuning a model to learn the structure needs data the team does not have, and still does not guarantee valid output.

§4 User Stories

Each story has acceptance criteria that a check in §5 tests.

US-1 · Documentation lead
As the documentation lead, I want each generated topic's model cost and edit ratio logged, so that I pay for tuning only when the log shows it pays.
Accepted when: every run writes one row with tokens, cost and attempts; log_pair adds the edit ratio after merge; the tuning rule in §5.9 reads only that table.

As the Cloud TPU writer, I want a first draft of each TPU7x topic built from its v6e and v5p siblings, so that I start from structure and sources, not from a copy.

As the information architect, I want generated topics to pass the same grammar and rules as hand-written topics, so that the content model holds as volume grows.

§5 Proposed Design

AlignR v0.1 is an agent built with Agent Development Kit (ADK), Google's open-source agent framework16. It uses Gemini 3.8 Flash (gemini-3.8-flash)17 in one mode only: structured output, where the model must return JSON that matches a JSON Schema9. Plain Python tools, called through function calling18, do the rest. They find siblings, write the XML and run the checks. The checks decide pass or fail, and the agent can't override them.

5.1 How it works

A writer opens an issue for a new generation set. AlignR reads three inputs that already exist: the launch values, the DITA set, and the content model. It drafts each topic, gates it, and opens one draft pull request per topic. Figure 6 is the same context as Figure 1, with AlignR added.

Figure 6

existing sourcedeterministic tool or outputmodelcheck that decidesretry path
The model sits in the middle of the agent, boxed in on both sides. Deterministic tools decide what it sees and what shape it must return. Checks decide whether its output reaches a person.

5.2 Two schema gates

The schema is the guardrail, twice. Gate 1 runs inside the Gemini API: the response must match the JSON Schema that AlignR built for this run. Gate 2 runs on the XML: the topic must be valid against the OASIS DITA grammar, which is normative in RELAX NG11. Between and after the gates, three checks catch what a grammar can't.

Figure 7

5.3 From the DITA content model to a JSON Schema

AlignR does not give Gemini the DITA grammar. Gemini accepts a subset of JSON Schema and may reject very large or deeply nested schemas9. Instead, build_schema maps one topic type to a small, flat JSON Schema. Figure 8 shows the mapping for a reference topic.

Figure 8
Reference topic: content model, JSON Schema field, serialised XML
DITA elementJSON field Gemini fillsXML Python writesopen question
The schema is built fresh for each run. Its enums list only the keys and source IDs that exist for this topic, so Gemini can't cite a source that isn't there or invent a key name.

This is an excerpt of the schema that build_schema produces for the TPU7x system architecture topic. JSON Schema keywords such as enum, required, minItems and additionalProperties are all supported in the Gemini API9. Google extended JSON Schema support to all actively supported Gemini models in November 202510.

// build_schema output (excerpt) · topic type: reference · run 0417
{
  "type": "object", "additionalProperties": false,
  "required": ["title", "shortdesc", "specs", "sections", "questions"],
  "properties": {
    "specs": { "type": "array", "minItems": 11, "maxItems": 11,

        "properties": {
          "label": { "type": "string" },
          "key":   { "enum": ["tpu7x-chips-per-pod", "tpu7x-bf16-tflops", "tpu7x-hbm-capacity", …] } } } },

The row count in specs comes from the sibling tables, not from the model. The siblings decide the layout.

5.4 Agent tools

The agent has ten tools. One calls the model. The others give the same result every time. The grounding check and the question placeholder come from The Autonomous Author7. Reading structure before calling a model comes from KnowledgeFlow8.

1. Find sibling topics find_siblings

Reads the DITA map. Returns the topics of the same type in the same place for earlier generations. It uses the map, not a search index.

output: 2 or 3 sibling topics, with their topic type and position

2. Load the new values load_facts

Reads the launch facts file and the existing key definitions. Gives each fact a source ID and records its unit.

output: facts with source IDs (S1 to Sn), values and units

3. Build the schema build_schema

Maps the topic type to a JSON Schema (Figure 8). Fills its enums with this run's keys and source IDs. Fixes table rows and columns from the siblings.

output: one JSON Schema for this topic and run, with a hash

4. Draft the topic generate_topic model

Calls Gemini 3.8 Flash with structured output. The prompt holds the siblings, the facts and the house style. On a revision, it holds only the failed fields and the reasons.

output: JSON that matches the schema (gate 1)

5. Write the XML serialise_dita

Turns the JSON into a DITA topic. Writes a keyref for every key. Replaces any literal value that matches a key. Writes questions as <draft-comment> and new keys as a map change.

output: one .dita file and, if needed, a key definition proposal

6. Validate the grammar validate_grammar gate 2

Validates the topic with lxml against the OASIS DITA RELAX NG grammars1112. Any error fails the run.

output: pass, or errors with line numbers

7. Check house rules check_rules check

Runs the information architect's Schematron rules with lxml.isoschematron13, then Vale with the Google package15. Some rules carry a safe automatic fix, such as sentence case in a title.

output: rule IDs that fail, fixes applied, Vale warnings

8. Check every value check_grounding check

Every number, unit, flag and command in the topic must match a fact or a key. Units must match as well as numbers, so GiB against GB fails.

output: grounded values out of all values, with each mismatch

9. Open the pull request open_pr

Opens a draft pull request with the report (§7). Assigns each question to the engineer or writer it names. The agent's account can't merge.

output: draft pull request and report comment

10. Log the edit log_pair

Runs on merge. Stores the agent's draft as rejected and the merged text as chosen, field by field, in the original AlignR pair format5. Adds the edit ratio and cost.

output: rows in the BigQuery edit log

5.5 Agent loop

The model decides how to fill each field. The checks decide whether it is done. Deterministic fixes run before any model revision, so the model is called again only for what code can't fix.

5.8 The edit log

The original AlignR design spent weeks collecting preference pairs before it could train5. In v0.1 the pairs collect themselves. Every merged pull request is a set of pairs: the agent's draft field and the writer's final field. The log is used first for cheap fixes, and only later, if ever, for training.

Figure 12
The edit log loop: repeated edits become rules first
The cheap path closes the loop: a rule costs nothing to run and never drifts. The dashed branch to tuning stays closed until the rule in §5.9 opens it.

5.9 When tuning pays

Fine-tuning is not a later phase of this MVP. It is a decision the edit log can make, with a fixed rule. Until the rule says yes, the cheaper fixes in §5.8 come first.

Tuning rule
  1. The log holds at least 12,000 accepted pairs for one topic type. This is the floor the original AlignR design set for one domain5.
  2. The edit ratio for that topic type has stopped falling for three launches in a row, after new rules and examples.
  3. A replay of held-out pairs shows that a tuned model saves more writer hours than its training and serving cost.
Figure 13
The tuning rule as a decision
Three gates, in order of cost to check. The first is a count, the second is a trend, and only the third needs a training experiment.

The numbers show why the rule is strict. Figure 14 models the cost of one draft attempt with today's prices. Tuning does not make a draft cheaper here. The newest Flash model with supervised fine-tuning on the price list is Gemini 3.5 Flash, and a tuned endpoint for Gemini 3 and later costs 1.5 times its base model19. Tuning can pay only through writer time.
